# 0016. 控制台默认运行用户改为非 root

- 日期：2026-11-06
- 状态：已接受

## 背景

控制台服务此前默认以 **root** 运行（仓库单元 `apps/web/backend/sandbox-console.service` 的 `User=root`）。这条默认口径在二期做启动模板时是**已知并接受**的——[[architecture/decisions/0010-启动模板收敛为控制台私有功能.md|ADR 0010]] 第 4 节把「服务以 root 身份运行时，`~` 展开为 `/root`，命中宿主敏感目录拒绝清单返回 400」写成既有契约的自然结果，不是缺陷。

但这条「已知并接受」在本轮被内置模板的落地打穿，原因链有四环：

1. **服务以 root 运行 → `~` 展开为 `/root`。** `~` 展开是网页创建专属口径：服务端把创建请求翻译成核心包请求时，只把**宿主路径段**的 `~` / `~/` 前缀换成**服务运行用户**的家目录；进程是 root 时该家目录就是 `/root`。
2. **内置 pi 模板 `tpl_pi_dev` 的五条凭证路径全走 `~`。** 该模板的配置体只含 `files` 一个键，下挂五条文件注入声明：宿主侧 `~/.ssh`（ssh 整目录）与 `~/.pi/agent/` 下的 `auth.json` / `models-store.json` / `models.json` / `settings.json`。
3. **五条路径一起展开到 `/root` 之下 → 命中核心包宿主敏感清单 → 400。** 清单是 `/etc`、`/proc`、`/sys`、`/dev`、`/boot`、`/root` 六个目录 + 宿主 Docker 套接字 + 平台数据根；文件注入在预检阶段按同一份清单拒绝宿主路径，命中即 400（拒绝发生在复制之前，原件零接触）。
4. **结果：内置模板在默认部署下必然不可用。** 这不是某台机器的环境问题，而是「默认 root」与「内置模板的凭证路径在 `~` 下」两条口径相撞的必然结果。

另一条线索说明这**不是平台设计所迫**：核心包的双轨设计本就支持非 root 运行——`apps/core/src/sandbox_platform/userspace.py` 的 `Privilege` 按进程身份分叉，进程本身是 root 时特权命令直跑，否则自动加 `sudo -n` 前缀（以沙箱用户身份执行时走 `sudo -n -u <用户>`）。也就是说，**控制面以非 root 身份运行是设计上已支持的路径**，缺的只是部署侧的默认配置与前置条件写明。

本机具备落地条件：`sankabox` 具备免密 sudo（`sankabox ALL=(ALL) NOPASSWD: ALL`）与 docker 组；仓库自带的单元里也已有完整的快照部署说明。

## 决策

### 1. 控制台默认以非 root 用户运行

- 仓库单元 `apps/web/backend/sandbox-console.service` 的 `User=` 由 `root` 改为 `sankabox`；单元头注释补齐五条前提（见下条）。仓库单元里 `User=` 与 `WorkingDirectory` / `ExecStart` / `SANDBOX_PLATFORM_HOME` 同属**占位**（按实际部署位置调整），换机器时须跟着改。
- **root 直跑仍是受支持的路径**：把 `User=` 改回 `root` 即可，**代码零改动**（`Privilege` 的 root 分支直跑特权命令、以 `setpriv` 切沙箱用户身份）。root 从「默认」降级为「受支持的非默认路径」。
- 代码侧的口径同步（文案不假设 root）：`apps/web/backend/sandbox_console/app.py` 与 `metadata.py` 的失败文案由「请以 root 运行控制面」中性化为「请确保运行用户对数据根目录可写（目录须已存在）」；`daemon.py` 的双轨注释与 `__main__.py` 的启动 docstring 同步。

### 2. 非 root 运行的五条前提（缺任一条即启动即报错或功能不可用）

1. **免密 sudo，且授权覆盖两条通道**：`sudo -n <宿主特权命令>`（以 root 跑 docker / useradd / install -d 等）与 `sudo -n -u <任意沙箱用户> <命令>`（以沙箱用户身份执行）都要能过。最常见的 `sankabox ALL=(root) NOPASSWD: ALL` **只覆盖前者**（`(root)` 把可切换的目标用户限定为 root），须用 `sankabox ALL=(ALL) NOPASSWD: ALL` 之类的片段。校验：`sudo -n true` 与 `sudo -n -u <某个沙箱用户> id`。
2. **平台数据根须已存在且属主为运行用户**：非 root 下平台**不会代建**数据根（配置层是普通 mkdir，父目录 `/var/lib` 不可写），目录不存在或不可写会**启动即报错**；数据根**之下**的子目录由平台经特权 `install -d` 创建，属主为运行用户。
3. **控制台监听端口 > 1024**：非 root 不能绑特权端口。
4. **`~` 展开目标是运行用户的家目录**（`sankabox` → `/home/sankabox`）：内置模板 `tpl_pi_dev` 需要的凭证放在该家目录下（`~/.ssh`、`~/.pi/agent/`）。展开依赖 systemd 按 `User=` 注入 `HOME`——用 `systemd-run` 临时起（未指定 `User=`）或手工前台跑时 `HOME` 可能缺失，展开目标不再是运行用户的家目录。
5. **部署快照与快照里的 venv 对运行用户可读可执行**：root 建的 venv 若 umask 收紧（目录 0700 / 文件 0600），非 root 的服务进程会 Permission denied 起不来，必要时 `sudo chmod -R a+rX <快照目录>`。

### 3. 数据根属主迁移的顺序（先属主、后改单元）

从 root 切到非 root 的**顺序不可颠倒**，否则新进程一起来就撞上属主不对导致的锁文件 / 元数据读写失败：

1. **先迁数据根属主**（排除 `registry-proxy` 子树）：
   ```
   sudo find /var/lib/sandbox-platform -path '*/registry-proxy*' -prune \
     -o ! -user sankabox -print0 | xargs -0 -r chown sankabox:sankabox
   ```
   `registry-proxy` 子树**属主保持原样**：它经特权通道创建 / 读写，证书直读失败时自动回退 sudo；裸 `chown -R` 会把 CA 私钥一起改属主。
2. **再改单元的 `User=`**（仓库单元与 `/etc/systemd/system` 下实际安装的那份都要改）。
3. **最后 `daemon-reload` + `restart`**，并按第 4 条验证。

### 4. 部署验证口径（本机已跑通）

- 进程身份：服务进程的 `USER=sankabox`、`HOME=/home/sankabox`。
- 接口可用：`GET /api/sandboxes` 返回 200。
- `~` 展开与敏感清单：离线干跑证明 `~/.ssh` 展开为 `/home/sankabox/.ssh` 后**通过**核心包的宿主敏感清单（原 `/root/.ssh` 会被 REJECT）。
- 回归：核心包 269 passed、后端 289 passed，ruff 干净。

### 5. 文档契约同步（仓库内文档，随本决策一并改写）

- `apps/web/backend/API.md` 第 13.3 节「内置模板的前置条件」：改为「仓库自带的 systemd 单元**默认以 `sankabox`（非 root）** 运行，五条宿主路径都展开到 `/home/sankabox` 之下，不命中敏感清单，创建沙箱正常通过」。
- 同文件第 13.4 节「root 运行的后果」：触发条件收窄为「**仅当自行把单元 `User` 改回 `root`** 时……命中敏感清单 → 400」。
- 仓库根 `README.md` 的「运行前提」段与单元头注释：补齐非 root 运行的前提清单与「非 root 默认不等于降权」的安全口径提醒。

## 影响

- **`~` 展开目标随运行用户走**：默认是 `/home/sankabox`，内置模板的五条凭证路径必须放在该家目录下。`~` 展开契约本身（ADR 0010）**没有被推翻**，变的只是运行身份带来的家目录取值。
- **信任边界没有变化——非 root 默认不等于降权。** 宿主特权操作仍经免密 sudo 执行，服务进程的**实际权限 ≈ root**：拿到访问令牌即等价于拿到宿主 root 级别的能力，这与 [[architecture/decisions/0009-二期控制台服务化与范围裁剪.md|ADR 0009]] 的风险论述（「服务以宿主特权身份运行，拿到接口就等价于拿到宿主 root 级别的能力，唯一有效防线是网络边界」）**完全一致**。要真正收敛权限，**必须收窄 sudoers 规则范围**（把 `NOPASSWD` 限定到平台真正用到的那几类命令），而不是靠改运行用户——代价是以后新增宿主命令必须同步补规则，漏一条就报权限错。
- **部署门槛上升**：部署方要额外准备免密 sudo（覆盖两条通道）、预先建好数据根并把属主交给运行用户、监听端口 > 1024、快照产物可读可执行。漏任一条会启动即报错或功能不可用——单元头注释与仓库 README 已把这五条写成清单。
- **数据根属主迁移是一次性动作，但回切 root 不需要迁回**：从非 root 切回 root 时，属主已经是 root 属主的场景要另行处理（同一台机器建议固定用一种身份操作控制面）。
- **root 直跑降级为受支持的非默认路径**：它的行为与代价不变（`~` 展开回 `/root` → 400 是既有契约，不是缺陷），只是不再由仓库单元默认推荐。
- **文档口径翻转**：接口文档里「root 运行 → `~` 展开 `/root` → 400」的表述仍然成立，但**触发条件变成「仅当自行把单元 `User` 改回 root」**；历史 ADR 的原有结论一律不改写，只补指向性更新。
- **平台侧不新增能力**：核心包、服务层与命令行代码**零行为变更**（只改了失败文案与注释）——本决策落在部署配置与文档口径上。
