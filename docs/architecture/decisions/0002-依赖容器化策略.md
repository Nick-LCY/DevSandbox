# 0002. 依赖容器化策略

- 日期：2026-10-29
- 状态：已接受

## 背景

沙箱里要跑真实的后端依赖：Postgres、MinIO（提供 S3 兼容接口）、Logto（单点登录）。这些依赖有两种可选形态：打进镜像的原生二进制，或独立容器。另有第三条路：用协议模拟器（例如单进程实现 S3 或单点登录的对外行为）顶替真实服务。

三种形态在镜像体积、行为真实性、复用性上差异很大，必须一次性定死，否则示例项目与端到端测试的结论都不可信。

## 决策

- 依赖一律容器化：Postgres、MinIO、Logto 以独立依赖容器运行在沙箱专属的每用户守护进程下，与沙箱容器同一守护进程、同一张内部网络。
- 不把服务做成原生二进制进镜像。理由是跨项目复用与版本独立演进：二进制一旦进镜像，升级某个依赖就要重打整个镜像。
- 不引入协议模拟器。模拟器的行为与真实实现不一致，端到端测试覆盖的是模拟行为，测试结论失去意义。
- MinIO 即真实 S3。AWS 只覆盖 S3 这一项能力，由 MinIO 提供；不再引入 LocalStack 之类的本地 AWS 模拟器。
- Logto 每沙箱自建一个容器实例，跑完即弃。当前估算单个实例占 150–300MB 内存、首次启动 10–30 秒；这两个数字是估算值，一期实测校准之后才作为规划依据。
- 依赖容器按需启动：沙箱运行时是否起 Postgres、MinIO、Logto，由 agent 自行决定，控制面不强制拉起。

## 影响

- 内存占用上升：单个沙箱若跑满三件套，Logto 一项就占 150–300MB。因此依赖容器必须能与沙箱容器分开停止，关闭沙箱时应顺带停掉依赖以释放内存。
- 启动延迟：Logto 首次启动 10–30 秒，需要靠依赖就绪探测与健康检查门禁吸收，否则端到端测试会因环境未就绪而假失败。
- 不使用模拟器，让端到端测试覆盖真实协议行为，结论可信；代价是依赖自身升级带来的不兼容会真实暴露出来，需要在示例项目里持续跟进版本。
- Logto 的资源数字尚未实测，一期必须校准；校准之前不要把它写进容量规划或对外承诺。
- 每沙箱自建 Logto 实例意味着认证状态不跨沙箱共享，这是「隔离优先」的有意取舍。
