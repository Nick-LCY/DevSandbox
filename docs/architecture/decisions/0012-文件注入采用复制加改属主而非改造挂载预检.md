# 0012. 文件注入采用复制加改属主而非改造挂载预检

- 日期：2026-11-02
- 状态：已接受

## 背景

平台把宿主文件带进沙箱的唯一通道是「用户声明挂载」，而挂载要过一道预检：平台在创建沙箱时以沙箱用户身份检查宿主路径「可读且可穿过」——实现是外部 `test -r` / `-x`，按 mode 位的属主 / 组 / 其他三位比对，**不识别 POSIX ACL**。预检不过，声明直接被拒。

这道预检让一批最常用的宿主文件进不了沙箱：ssh 私钥与 pi 凭证 `auth.json` 通常是 0600，目录常是 0700。它们的属主是用户本人，mode 位上沙箱用户既不是属主也不在匹配组里，预检必然失败。

绕不过去的根因是**时序**，不是权限模型本身：

- 沙箱用户在创建那一刻才建立，uid 动态分配、创建失败即回滚删除。所以「提前给某个用户 / 组授权」在时序上没有授权对象——ACL 条目与专用组都要指向一个具体的 uid，而那一刻它还不存在。
- 敏感原件不能靠放开权限位解决。0600 / 0700 的原件一旦放开其他用户位，本机所有本地账号都能读私钥与凭证，暴露面失控。

四条替代路线都评估过，逐条否决：

1. **给宿主文件加 ACL 授权** — 预检按 mode 位比对、看不见 ACL，等于要把预检整体改造成 ACL 感知，还得要求宿主装 acl 包并改造创建主路径；改造成本与新增依赖都压在预检这条关键路径上。
2. **放开原件的其他用户位** — 本机所有本地账号可读私钥与凭证，暴露面失控，等于为一次性的沙箱需求永久放宽宿主凭证。
3. **人工维护中转副本** — 副本脱管：内容要人工同步、副本何时清理靠人记，清理不及时就是一份新的长期暴露面。
4. **改用 HTTPS + 访问令牌替代 ssh 密钥** — 改变了既有的 ssh 使用习惯，且令牌文件本身的权限问题同源：照样需要一份沙箱用户读得到的宿主文件，预检照样拦。

选定机制是**在创建流程内做「复制 + 改属主」**：时序上排在专属用户创建之后、沙箱容器启动之前，把用户声明的宿主文件复制到沙箱用户家目录内的暂存目录，属主改成沙箱用户，再以只读方式挂进容器。本决策把这条机制连同它的信任边界一次写死。

## 决策

### 1. 注入是创建流程内的一步：复制、改属主、只读挂载

- 注入发生在**专属用户创建之后、沙箱容器启动之前**，是七步创建流程之外的一步旁路；它失败即回滚——删掉整个暂存目录，不在宿主上留半截副本。
- 副本落**沙箱用户家目录内的暂存目录** `.sandbox-files/`：暂存目录权限 0700、目录内文件权限 0600，属主与主组都是沙箱用户（用 uid / gid 数值设置，不依赖「主组与用户同名」的假设）；免 root 守护进程以该用户身份运行，能穿过暂存目录把副本挂进容器。
- 复制与改属主经**与建用户同一条特权通道**执行，不新增特权机制。
- 副本以**只读**方式挂进容器，容器内一律不可写，也不支持容器写回宿主。
- **注入不走挂载那道可读性预检**：副本属主就是沙箱用户，那道预检对注入没有意义。

### 2. 原件零接触，副本与沙箱同寿，复制是创建时快照

- **原件零接触**：注入过程对原件只读取——不 chmod、不 chown、不修改、不删除；原件的权限位、属主、内容、mtime 一律不变。
- **副本与沙箱同寿**：副本落在沙箱用户家目录里，随沙箱删除时的「回收用户家目录」一起消失；停止 / 启动期间保留。
- **复制是创建时快照**：宿主原件之后的变更**不回灌**到沙箱，要新鲜内容就重建沙箱。
- **启动时副本缺失即报错阻断**：启动沙箱前逐条特权探测副本还在不在，副本没了直接报「注入文件副本已不存在，无法启动沙箱」，不让 Docker 静默建一个空目录挂进容器。

### 3. 校验：归一化与真实路径双重比对，敏感清单沿用挂载那套

- **路径先归一化再校验**：折叠 `.` / `..` 并把前导多斜杠压成一个，`//etc/shadow` 这类变体绕不过按 `/etc` 根比对的敏感清单。
- **双重校验**：词法归一化后比一遍受限范围；再用 `readlink -f` 解析出符号链接指向的**真实路径**再比一遍——中间某一段是符号链接的情况（`/tmp/link/secret`，`link` 指向受限目录）词法上看不出来，只有真实路径看得穿。
- **敏感目录拒绝清单沿用挂载那套**（宿主固定敏感清单 + 平台数据根等调用方追加项），不另立一套。
- **注入源不得位于任何已存在的沙箱用户家目录内**（含本次目标沙箱自己的家目录）：家目录集合经 `getent passwd` 按平台沙箱用户名前缀现查枚举，取 passwd 里的家目录字段，**不依赖 `/home` 固定根**（宿主把家目录放在别处同样覆盖得到）；条目残留但目录已删的不算。
- **目录树内的符号链接与非常规文件一律拒绝**：目录里的符号链接会把断链或预期外的内容带进沙箱；FIFO / 设备 / 套接字在容器里没有意义，复制时还可能阻塞。
- **声明路径本身就是符号链接时一律拒绝**：既不跟随、也不复制链接本身。

### 4. 信任边界：注入源由平台以特权身份读取，调用者视为受信主体

- 注入源由平台**以特权身份读取**（复制动作走特权通道）：控制台 / 命令行的调用者被视为**平台受信主体**，**文件注入不提供跨账号隔离**。
- 受限范围只有三块：**宿主敏感清单**、**任何已存在的沙箱用户家目录**、**平台数据根**。黑名单之外的、root 可读的文件**均可注入**——这是该功能的本质（把 0600 的凭证送进沙箱），**不是缺陷**。
- 这条口径继承控制台「不做认证、只绑回环或内网」的部署前提（见 [[architecture/decisions/0009-二期控制台服务化与范围裁剪.md|0009 二期控制台服务化与范围裁剪]]）；部署到多用户共享环境前必须另加认证与调用者鉴权，本决策不覆盖那种场景。

### 5. 范围口径：字段同名同格式，模板合并语义与 `~` 展开沿用既有口径

- 核心包 `CreateRequest.files` 与控制台 `CreateSandboxRequest.files` / `TemplateConfig.files` **同名同格式**：`宿主路径:容器路径`，固定两段，**强制只读**（没有读写标记段，第三段按格式非法拒绝）。
- **模板合并语义沿用既有口径**：`files` 与挂载列表一样**整组替换**——模板里出现 `files` 就整体替换表单的文件注入行，没出现就保持现状（见 [[architecture/decisions/0010-启动模板收敛为控制台私有功能.md|0010 启动模板收敛为控制台私有功能]]）。
- **`~` 展开仅作用于宿主路径段**，容器路径段不展开；这是网页创建专属口径（命令行仍要求绝对路径）。
- **命令行零改动**：`sandboxctl` 本轮不加注入参数，「增加 `--file` 参数」登记为待办。
- **会话持久化不在本需求**：按用户另有方案另行解决。

## 影响

- **验收**：核心包 pytest **245 项全绿**（一轮前基线 195）、root 级 23 项全绿；服务端 pytest **184 项全绿**（基线 172）；ruff（E4/E7/E9/F）退出码 0；前端 vitest **317 项全绿**（基线 274），typecheck / typecheck:tests / build 全绿；Playwright 真机 **27 条全绿**（基线 24，新增 3 条文件注入用例）；命令行零改动。
- **提交链**：核心包 `c2535eb` → 服务端 `95e16f0` → 前端 `d51b313` → 审查修复一轮 `b05e041` + `c5ca70f` → 真机用例 `f52a493` → 审查修复二轮 `81219f7`。
- **两轮审查修复的落点**：一轮修路径归一化、注入源范围收口与副本存在性校验；二轮修双斜杠绕过、家目录口径统一与真实路径复核。
- **快照语义是显式代价**：宿主凭证轮换后沙箱里仍是旧副本，要新鲜内容必须重建沙箱——不设「重新注入」入口，此代价必须在用户文档明示。
- **注入副本不是用户声明挂载**：它不进回收清单里「用户挂载的宿主机目录不受影响」那一份，也不作为用户挂载逐条展示；它随家目录整体回收。
- **跨账号隔离不存在**：能触达平台创建入口的一方，就能把 root 可读的文件送进自己的沙箱。这是本机制的边界，不是漏洞。
- **命令行没有入口**：本轮命令行零改动，`--file` 参数待补。
