# 0001. 项目定位与三期路线

- 日期：2026-10-29
- 状态：已接受

## 背景

本项目要解决的问题是：让 pi agent 拥有一个隔离、可复用的全栈开发沙箱，能在里面自主完成端到端测试——用 Playwright 操作真实浏览器，并把截图作为多模态反馈交回给 agent 自己判断。

最终产品形态是网站平台：随时启动一个沙箱镜像、在网页终端里指挥 agent、通过 URL 代理访问容器端口。这三件事跨度很大，如果不先划清阶段，很容易在一期做出一个「只能本地手玩的原型」，再在二期推倒重来。

需要先拍板三件事：项目用什么衡量成功、分几期交付、哪些架构约束必须跨期保持。

## 决策

### 1. 核心价值锚点是端到端测试闭环

沙箱的成败标准不是「容器能跑起来」，而是 agent 能否独立完成这条闭环：

改码 → 起环境 → 跑端到端 → 看截图 → 修复 → 全绿。

闭环里任何一环由人代劳，都算未达标。

### 2. 三期路线

| 期次 | 目标 | 主要交付 |
|---|---|---|
| 一期 | 本地闭环 | 免 root 打样验证 → 镜像 → 生命周期模块与命令行 → 端到端测试基建 → 示例项目验收 |
| 二期 | 控制面服务化 | FastAPI 生命周期接口 + 网页终端（tmux 式附着、断线重连）；控制台自身用 Logto 认证 |
| 三期 | 代理与多沙箱运营 | URL 代理、资源配额、快照、自动清理、厚沙箱模式、可选弱网模拟 |

### 3. 跨期必须保持的两条架构约束

- 控制面逻辑从一期就写成可复用服务模块，命令行只是薄壳。二期换成 FastAPI 接口时不需要改写核心逻辑。
- 镜像即产品：一切环境差异通过挂载注入，而不是靠修改镜像。镜像版本一旦发布，就不应因某个用户的环境要求而重新打包。

### 4. 一期验收标准

- 选一个真实全栈示例项目：前端 React / Vue / Astro 任选，后端 FastAPI，数据层 Postgres + MinIO + Logto。
- agent 独立跑通「改码 → 起环境 → 端到端 → 看截图 → 修复 → 全绿」循环。
- 全程无需人工介入。

## 影响

- 一期范围被压在本地闭环，网站与多沙箱运营都不做；换来的是最快验证最不可替代的部分——免 root 隔离与端到端闭环是否真的成立。
- 控制面从第一天就是服务模块，多一层抽象成本，但避免了二期整体重构。
- 「镜像即产品」把镜像发布变成正式产出物，需要版本管理与变更纪律，发布流程的重量提前落到一期。
- 一期验收标准是硬门槛：其余部分再完整，只要 agent 无法自主闭环，一期就不算完成。
