# 0008. 统一镜像代理与离线包废弃

- 日期：2026-10-29
- 状态：已接受

## 背景

一期落地的是「离线包」做法：把 Postgres、MinIO、Logto 三个依赖镜像打成 tar 随平台基础镜像分发，沙箱首启自动 `docker load`。这条路在三个方向上到了天花板：

- **体积**：三个离线包合计 489.5 MB，占基础镜像 534.4 MB 的九成。基础镜像名义上极简，实质是三个依赖镜像的搬运工。
- **维护成本随镜像数量线性增长**：每新增一个依赖镜像，就多一个 tar、多一条清单、多一次校验和与一次打包发布，发布节奏被依赖版本绑死。
- **覆盖不了非 Docker Hub 的仓库**：docker 的 `--registry-mirror` 这类镜像加速器只对 Docker Hub 生效，GHCR 等仓库的镜像（如 Logto）无法纳入统一入口，来源分裂的问题原样保留。

用户的真实目标有两条：省流量（同一个依赖镜像不要反复从公网拉）与来源统一（所有外部镜像从一个入口取得，便于审计与缓存）。离线包只满足前一条的一半——它靠分发实现省流量，代价是基础镜像膨胀；后一条完全没解决。

替代方案的评估结论：docker 原生的镜像加速器只覆盖 Docker Hub，而 HTTP 层的透明缓存代理在网络层拦截请求，对 docker 客户端与守护进程透明、对任意仓库（含 ghcr.io）一视同仁。因此改用后者。

## 决策

### 1. 废弃离线包机制，镜像来源统一经统一镜像代理

- 平台基础镜像不再内置 postgres / minio / logto 的离线 tar：镜像内不再有 `/opt/deps/images/` 目录，也不再有 `load-deps.sh` 与 `fetch-deps.sh` 两个脚本。
- 三件套（Postgres / MinIO / Logto）以及一切外部镜像，统一经统一镜像代理拉取。代理采用 rpardini 项目的 docker-registry-proxy（MITM 透明缓存代理）：缓存命中走本地，未命中由代理拉一次外网并写入缓存。
- 选型理由记死：代理在 HTTP 层拦截，对任意仓库透明，一次配置即覆盖全部镜像来源。

### 2. 宿主导出注入保留但收窄

- `save` / `load` 机制保留，仅用于本地构建、不存在于任何仓库的平台镜像（例如只在宿主构建出来的 `sandbox-default`）。
- 仓库中存在的镜像一律走代理拉取，不再走导出注入。

### 3. 代理不可达即失败，不做降级直连

- 代理不可达时，拉取直接失败；不自动降级为直连公网。
- 控制面在创建沙箱时自动拉起代理容器并做健康检查；代理仍不可达则明确报错，不静默继续。

### 4. 代理以容器形式跑在宿主 root 守护进程

- 代理容器运行在宿主 root 守护进程下，绑定回环地址，不对外暴露。
- 缓存目录与 CA 证书存放在平台数据根目录下。
- CA 私钥属敏感资产，文件权限收紧。
- 沙箱守护进程的 systemd 单元注入 `HTTPS_PROXY`、`NO_PROXY`、`SSL_CERT_FILE` 三个环境变量。其中 `SSL_CERT_FILE` 指向合并后的证书文件（系统 CA 束 + 代理 CA），避免只认代理 CA 而破坏非代理的 TLS 连接。

### 5. 本轮范围

- 本轮只重建平台基础镜像（0.2.0），并用小镜像实测 pull 通路。
- 默认全栈沙箱镜像暂不重建，仍为 0.1.0，其中仍含离线包层，属已知过渡状态。

## 影响

- **代理成为单点**：代理不可达则镜像拉取全部失败。这是用户明确接受的取舍（宁可失败也不走无审计直连），代价是宿主网络异常会直接卡住沙箱创建。
- **标签漂移与缓存滞后**：代理按镜像引用（含 tag）缓存。tag 被上游重新指向新镜像时，缓存里仍是旧内容，直到缓存过期或被清理为止。因此依赖镜像必须钉死 tag 或 digest，不能用 `latest` 一类浮动标签。
- **CA 私钥落在宿主磁盘**，属于敏感资产：权限收紧只降低风险、不能消除风险；代理一旦被攻破，经它中转的流量可被解密。
- **缓存目录只增不减**：长期运行会持续占用宿主磁盘。缓存 GC 命令尚未实现，已登记为待办（见 [[current-state.md|当前状态]] 的 TODO 区）。
- **冷启动变慢**：缓存为空时代理需从外网拉一遍，冷缓存下首个沙箱首次起依赖约 1–2 分钟；之后命中缓存即快。
- **基础镜像瘦身且发布解耦**：镜像不再随依赖镜像膨胀（离线包曾占 489.5 MB），基础镜像的构建与发布不再被依赖版本绑死。
