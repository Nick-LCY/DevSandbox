# 0009. 二期控制台服务化与范围裁剪

- 日期：2026-10-30
- 状态：已接受

## 背景

一期 PRD 给二期定的目标是「FastAPI 生命周期接口 + 网页终端 + Logto 认证」三件套。但二期的真实使用形态比这条规划窄得多：这套平台是**内部部署、个人使用**的——一个人在一台自己管的宿主机上，起沙箱、看沙箱、指挥 agent 干活，不存在第二个使用者，也不需要把平台开放给外部。

规划形态与实际形态的错位，带来三个必须在二期开动前就拍板的问题：

1. **认证要不要做**。原规划里的 Logto 认证是为多用户公开部署设计的。在个人自用的形态下，它不减风险、只增成本：多一套认证依赖、多一个登录流程、多一处凭据管理，还把「访问控制」这件事变成需要长期维护的系统工程。
2. **命令行要不要改造成服务客户端**。一期的跨期约束写着「二期把命令行换成 FastAPI 接口」。但二期的核心是「网页与命令行共用同一套控制面逻辑」，而不是「命令行必须走 HTTP」——后者只是实现路径的选择，不是跨期约束的必要条件。
3. **网页创建沙箱时，启动镜像从哪来**。统一镜像代理解决的是「依赖镜像（Postgres / MinIO / Logto 等）的来源统一与缓存」，但沙箱启动镜像是用户自己构建的产物：它在宿主本地构建、可能根本不存在于任何仓库，代理拉不到它。若不把这条路径单独定下来，网页端就选不到本地镜像。

二期交付过程中又在终端能力上做了两个收口决定：会话如何保活（容器内工具 vs. 服务侧自研）、以及服务重启后旧会话怎么办。这两条此前没有决策记录。

本决策把上述口径一次写死，作为二期的收口文档。

## 决策

### 1. 不做认证：安全边界改为网络边界

- 系统面向内部部署、个人使用，**控制台与接口不做任何认证，也不做多用户隔离**。
- 安全边界改为「**服务只绑回环或内网地址、不得暴露公网**」；绑非回环地址时，启动过程打醒目告警，把「这不是隔离边界」这件事摆到最显眼处。
- 交互式接口文档（`/docs`）默认关闭，需要时用环境变量显式开启。
- 一期 PRD 规划的 Logto 认证在本期裁剪。三期是否引入，视届时的部署形态再议——若平台要从「个人自用」变成「多用户访问」，认证必须重新成为硬需求。（三期现指桌面端打包轮；认证与部署形态的排期留待其立项时定，见 [[architecture/decisions/0001-项目定位与三期路线.md|ADR 0001 修订行（2026-11-03 三期方向改定）]]。）

### 2. 命令行保持直连，不改造为服务客户端

- 一期的跨期约束「二期把命令行换成 FastAPI 接口」**推迟**。二期结束时命令行 `sandboxctl` 仍直连控制面核心包，源码一行未改。
- 理由有两条：
  - 个人使用下，网页与命令行同时操作同一个沙箱的概率极低；而控制面核心包已有**按沙箱名互斥**与**原子占名**兜底，同名并发创建的互相拆台问题在服务化后已被根治。
  - 使用纪律明确为「**同一沙箱避免网页与命令行同时操作**」；纪律比双入口一致性的技术保证更便宜。
- 命令行服务化延后执行。届时 CLI 改为 HTTP 客户端即可——控制面核心包与命令行的调用关系没有变化，改造点集中在参数组装与结果渲染。

### 3. 沙箱启动镜像来源 = 宿主本地 + 导出注入

- 网页创建沙箱时，**实时枚举宿主 Docker 本地镜像**供用户直接选用，包含任何本地构建、不存在于任何仓库的镜像。选定后经既有的**宿主导出注入**机制进入该沙箱的守护进程。
- **不做网页拉取镜像，不做镜像选项清单**。镜像清单不缓存、不预置、不维护版本列表——枚举宿主本地状态是唯一准确口径。
- 镜像代理的职责收窄为「**只服务各沙箱守护进程的依赖镜像拉取**」；宿主 Docker 的配置一律不动（不配代理、不加镜像加速）。
- 宿主本地没有该镜像时，按**用户错误报 400**（请求错误），**不降级为经代理拉取**——静默改换镜像来源会让用户拿到与预期不同的镜像环境。

### 4. 网页终端自研伪终端桥接

- **不引入 tmux / abduco / dtach**。这三个工具的共同代价是要进沙箱镜像，也就意味着改镜像、重建镜像、重发版；服务侧自研则只动宿主，不动镜像。
- 实现方式：服务侧以**宿主伪终端承载容器内真实 TTY**，经 WebSocket 与浏览器双向桥接。容器内进程拿到的是真 TTY，行编辑与全屏程序照常工作。
- 会话语义：

| 场景 | 口径 |
|---|---|
| 同一沙箱多终端 | 各自独立，互不串扰 |
| 浏览器断开 | 会话保留，输出继续写入环形缓冲；重连携带原会话标识先回放缓冲再接实时流，现场不丢 |
| 服务重启 | **会话全部丢失**（已确认接受）；启动时按记录的进程号终止遗留 exec 进程 |
| 用户手动 exit 退出的会话 | **保留显示，手动删除**；不自动清理 |
| 运行中的会话 | 可「关闭并移除」：关闭会话并**清理容器内进程树**，同时删记录 |
| 空闲回收 | **只针对运行中且无附着的会话**；已退出的会话不参与回收 |

- 控制面核心包新增**按名互斥与原子占名**：这是服务化带来的并发面，服务层与命令行同受益（互斥落在核心包，与免 root 分层一致：宿主交互收敛在核心包，服务层只做编排与转译）。

## 影响

- **无认证意味着内网暴露即完全信任**。服务以宿主特权身份运行，拿到接口就等价于拿到宿主 root 级别的能力；唯一有效的防线是网络边界（只绑回环或内网）。这条边界一旦被突破，没有第二层拦截。这是本决策最大的风险敞口，已知并接受。
- **双入口并存有状态不一致窗口**。网页与命令行各自直连核心包，同一沙箱被两边同时操作时，状态可能不一致。该窗口靠使用纪律而非技术手段约束。
- **终端会话不落容器内保活**，服务重启则会话现场全丢。用户正在跑的交互式程序（如未退出的编辑器、构建进程）会随服务进程一并消失。
- **已退出的会话仍占终端名额**，需用户手动删除；名额有上限（全局与单沙箱各有限制），占满时新建终端会报错并提示清理入口。
- **核心包新增 FastAPI / uvicorn 依赖，打破了「核心包零第三方依赖」的现状**。接受该代价：依赖统一由 uv 管理，单包 `uv sync` 即可装齐，不引入多套包管理口径。
- 附带收益：核心包的按名互斥与原子占名让命令行侧也免疫同名并发创建，此前只有服务侧暴露该并发面。
