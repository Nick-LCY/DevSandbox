# 0014. 端口转发机制选型

- 日期：2026-11-03
- 状态：已接受

## 背景

桌面端要访问沙箱里的服务端口，而沙箱容器与依赖容器跑在**每沙箱专属的免 root 守护进程**下，处在 slirp4netns 网络命名空间里。宿主网络与沙箱网络之间没有任何路由——这正是 [[architecture/decisions/0003-每沙箱专属用户与免root守护进程.md|ADR 0003]] 第 5 节「不做宿主机端口发布、不用 nsenter 把宿主机网卡桥接进容器」的隔离设计。

要打通这条路，本期提出的机制是：用户显式指定「沙箱名 + 容器端口」，平台起一个**转发容器**接入沙箱网络，由沙箱的免 root 守护进程用 `-p` 把转发容器端口发布到**后端宿主回环**，再由后端服务经一条隧道把字节送到桌面端，桌面端在自己机器的回环上开监听。

这条链路上有三个必须先钉死的点：

**第一，「`-p` 发布宿主回环」在本平台是否有先例。** 全仓唯一的 `-p` 用法在统一镜像代理 `apps/core/src/sandbox_platform/proxy.py`：`-p 127.0.0.1:3128:3128`。但那个容器是**宿主 root 守护进程**起的——`Privilege.wrap()` 在进程本身是 root 时不加前缀，走的是宿主 `docker`，不是沙箱的免 root 守护进程。而沙箱的免 root 守护进程按 `userspace.py` 固定了 `DOCKERD_ROOTLESS_ROOTLESSKIT_DETACH_NETNS=true`（守护进程留在宿主网络命名空间、只有容器在 slirp4netns 命名空间里）。免 root 守护进程下 `-p` 能否在宿主回环真的产生监听，**本仓库从未验证过**；一期打样任务 `01-rootless-probe.md` 的「端口发布判定」写的恰恰是宿主 `ss -ltn` **不出现**由探针容器新增的监听端口。因此这条路径在本期是**未知**，必须作为硬前置打样项。

**第二，转发容器归谁、谁回收。** 平台只回收自建资源。转发容器是平台自建的，必须进回收清单；而沙箱容器与依赖容器**零改动**（ADR 0003 的隔离契约不动），用户的沙箱镜像也**零改动**（镜像即产品的跨期约束）。

**第三，隧道这一跳的语义。** 隧道要跨机器（桌面端可能在另一台机器上），要支持同一沙箱的多个端口、同一端口的多条并发连接，还要有明确的断开 / 停止 / 服务重启语义。既有终端会话已经有一套成熟的口径（「服务重启即丢」），端口转发应当与之对齐而不是另发明一套。

## 决策

### 1. 端口转发的语义边界

- **只转发「用户显式指定的沙箱中的特定端口」**：不提供「转发沙箱全部端口」，不提供「自动发现端口」，不提供「按端口区间转发」。
- **监听面只在本机回环**：桌面端在**桌面所在机器**的 `127.0.0.1` 上开监听；后端侧在**后端宿主**的 `127.0.0.1` 上开端口。两端都只绑回环，**都不出本机**。
- **明确区分于 URL 代理**：URL 代理是「容器端口发布到宿主回环后，由宿主页反代对外提供一个可分享的网址」，已随原定三期整体退役（[[architecture/decisions/0001-项目定位与三期路线.md|ADR 0001]] 修订行）。端口转发是「桌面应用直连沙箱端口」，没有对外的网页入口、没有反代层、没有可分享地址。词汇表必须保持这一区分。

### 2. 转发容器：平台自建，接沙箱网络，由沙箱守护进程起

- 转发容器名 `<沙箱名>-fwd-<端口>`，带平台标签（用于枚举与回收）。
- 镜像：平台自有的转发镜像（`alpine/socat`，钉 digest），经统一镜像代理拉取到**沙箱的守护进程**（镜像拉取走代理是 ADR 0009 的既有口径）。**不改任何沙箱镜像**，用户镜像里不需要有 `socat`。
- 命令：`socat TCP-LISTEN:<内部端口>,fork,reuseaddr TCP:<沙箱容器名>:<用户端口>`；`--restart=no`（生命周期由平台显式管理）。
- **由沙箱自己的免 root 守护进程启动**：只有这样它才能接入沙箱网络并按容器名解析沙箱容器。沙箱容器与依赖容器本身零改动。
- **端口发布用 `-p 127.0.0.1:<宿主端口>:<内部端口>`**，复用 `proxy.py` 的 `-p 127.0.0.1:<port>:<port>` 写法与「只绑回环」的口径。

### 3. 免 root `-p` 是硬前置打样项，不成立则走 Fallback B

- 打样判定（P1）：在沙箱守护进程下 `docker run -p 127.0.0.1:<宿主端口>:<容器端口>`，判据是「宿主 `ss -ltn` 出现该端口」且「从宿主 `curl 127.0.0.1:<端口>` 能连到容器内目标服务」。
- **Fallback B（`-p` 不成立时的备案路径）**：转发容器仍起、仍接沙箱网络，但**不发布端口**；宿主侧改用 `docker exec -i <转发容器> socat - TCP:<沙箱容器>:<端口>` 建立双向字节管道，平台侧把字节泵到宿主回环端口。
  - 代价：每条连接一个 exec 进程；延迟与吞吐不如直连；`exec` 管道非 TTY，需要额外分帧与超时处理。
  - 优点：完全不依赖 `-p`，只依赖终端伪终端桥接已经在用的 `docker exec` 机制。
- **两条路径的外层契约完全一致**（宿主侧暴露一个回环端口、后端隧道连它、桌面端开本机监听），因此 Fallback B 的切换不影响上层任何一层。

### 4. 宿主端口自动分配与占位

- 后端宿主回环端口由平台自动分配（可配区间，默认 `18000-18999`），分配前做「端口可绑定」探测。
- 分配结果落进转发记录形成**占位**；启动转发容器时若 Docker 绑定失败（端口被占）则换端口重试，仍失败则明确报错。
- 端口与转发记录一一对应，停止转发即释放。

### 5. 隧道协议

- 路径：`/api/forward/tunnel/{forward_id}`；**一条 WebSocket 对一条 TCP 连接**（本期不做多路复用）。
- 客户端 → 服务端：二进制帧 = 透传字节；文本帧 = 控制（本期仅留扩展位）。
- 服务端 → 客户端：二进制帧 = 透传字节；文本帧 = `{"type":"hello", ...}` / `{"type":"error","message":"..."}`。
- 关闭：任一侧 EOF 即关另一侧；转发不存在或已停止 → 关闭码 `1008`；正常关闭 `1000`。
- 鉴权：桌面 Rust 客户端可以直接设 `Authorization: Bearer`，**不需要票据**（票据只服务于浏览器侧的 WebSocket）。
- 帧协议风格与终端桥接保持一致（二进制 = 字节、文本 = 控制），便于前端 / Rust 两侧共用同一套心智。

### 6. 转发管理 REST

- `GET /api/forwards` → 裸数组（与既有接口风格一致）。
- `POST /api/forwards` → 入参 `{sandbox, port}`；沙箱不存在 / 已停止 / 端口非法 → 明确错误。
- `DELETE /api/forwards/{id}` → 停止转发：停并删转发容器、释放宿主端口、删记录。

### 7. 生命周期与清理语义

| 场景 | 口径 |
|---|---|
| 建立转发 | 记录 + 分配宿主端口 + 起转发容器（幂等：同名同端口的转发容器已存在则复用） |
| 沙箱停止 | 该沙箱的转发容器一并停止；**记录保留** |
| 沙箱启动 | 不自动重建；隧道建立时若容器缺失则幂等重建 |
| 停止转发 | 停并删转发容器 + 释放宿主端口 + 删记录 |
| 沙箱删除 | 转发容器与转发记录**纳入回收清单并被回收**（平台自建资源） |
| 后端服务重启 | **全部转发会话丢失**，启动时清理上次遗留的转发容器与记录（对齐终端会话「服务重启即丢」） |
| 桌面端断开 | 隧道 WS 断开即关本机监听；界面显示「转发已断开」 |

### 8. 能力落点

- 转发编排（容器起停、端口分配、标签枚举、清理）落**核心包** `apps/core/src/sandbox_platform/forwarding.py`，是可复用服务模块；服务端（`sandbox_console`）只做编排与转译。命令行本期不接（命令行不改是 ADR 0009 的既有口径）。

## 影响

- **免 root `-p` 是本决策最大的未知**。若 P1 打样不通过，Fallback B 会带来明显的性能与复杂度代价（每连接一个 exec 进程）。这条不确定性必须在 PRD 的风险清单与打样任务里显式登记，不能默认它成立。
- **宿主回环这一跳不受令牌保护**。后端宿主上的任意本地进程都能直连被发布的端口（回环上的本地访问不需要凭据）。这是与已退役的 URL 代理同性质、但暴露面小得多的边界（不提供网页入口、不出局域网）。本期接受并写进文档；后续如需收紧，方向是「宿主回环端口只在隧道建立期间短暂开启」或「宿主回环端口加一个平台内部口令」。
- **端口转发不是 URL 代理，但极易被误读**。两者在「容器端口发布到宿主回环」这一步上形态相似，区别在「谁访问、暴露到哪」。词汇表必须显式区分，界面文案也要写明「访问端口需要桌面应用」。
- **多路复用被推迟**：一条 WS 对一条连接，简单可靠，但每条 TCP 连接多一次 WS 握手。高并发场景（如浏览器同时开几十个并发请求到同一个沙箱端口）会有握手开销。这是可接受的取舍，因为本期目标是开发调试场景。
- **服务重启丢转发会话**会让用户重连时需要重建。沿用终端会话的既有口径而不是发明新语义，是为了少一套状态机、少一类用户困惑。
- **转发容器是新的平台自建资源**，意味着删除沙箱的回收清单多了一项、`reclaim_plan` 的输出变了，既有验收里断言回收清单结构的用例要跟着更新。
- **用户镜像零改动**这条守住了（转发容器是独立的平台镜像），但代价是多了一个需要平台自己维护的镜像（拉取、digest 固定、代理缓存命中）。
