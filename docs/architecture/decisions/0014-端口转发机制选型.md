# 0014. 端口转发机制选型

- 日期：2026-11-03
- 修订：2026-11-03（**第二次修订，决策 C：端口转发链路两点化——后端宿主机零端口**——转发只建立在「沙箱 ⇄ 用户机（桌面应用 / CLI）」之间，后端宿主机**不再发布任何端口**；`-p` 主路径与宿主端口区间（默认 `18000-18999`）分配**整体废除**——**不是「`-p` 不可用」：P1 已实测可用**，而是产品形态上后端宿主机不该持有端口；Fallback B（`docker exec -i` 字节泵）**升为唯一路径**，「每连接一个 exec 进程」的代价从「备案待评估」转为**既定既接受**；用户机侧端口规则改为：默认 = 容器端口、可编辑、**不可为空**、被占自动换空闲并显示实际值、允许 <1024。第 1~8 节按此改写，「影响」段同步。*第一次修订 = 同日 P1 打样结论并入（`-p` 在免 root 守护进程下实测成立，留档见 [[tasks/phase3-desktop/RESULTS.md|三期留档]]）*，*第三次修订（2026-11-03，实现轮）= 第 7 节「桌面端断开」一行按桌面侧实现修订：单条隧道断开只关那一条连接，本机监听保留到用户显式停止*）
- 状态：已接受

## 背景

桌面端要访问沙箱里的服务端口，而沙箱容器与依赖容器跑在**每沙箱专属的免 root 守护进程**下，处在 slirp4netns 网络命名空间里。宿主网络与沙箱网络之间没有任何路由——这正是 [[architecture/decisions/0003-每沙箱专属用户与免root守护进程.md|ADR 0003]] 第 5 节「不做宿主机端口发布、不用 nsenter 把宿主机网卡桥接进容器」的隔离设计。

> **2026-11-03 决策 C 修订（链路两点化）**：本决策立稿时的链路是「沙箱 → 转发容器 → **后端宿主回环端口** → 后端隧道 → 桌面端本机监听」，**后端宿主是链路的一端、持有一个被发布到宿主回环的端口**。修订后链路**只有两点**——「沙箱 ⇄ 用户机」——后端宿主退化为**纯中继**（跑隧道服务与字节泵，**不发布端口、不监听端口**）。立稿口径全文保留在各节留档标注处。

要打通这条路，本期提出的机制是：用户显式指定「沙箱名 + 容器端口」，平台起一个**转发容器**接入沙箱网络，由沙箱的免 root 守护进程用 `-p` 把转发容器端口发布到**后端宿主回环**，再由后端服务经一条隧道把字节送到桌面端，桌面端在自己机器的回环上开监听。（**2026-11-03 决策 C 修订：上述立稿机制整体作废**，改为「转发容器**不发布端口** + 后端用 `docker exec -i` 起字节泵」，详见第 2、3 节。）

这条链路上有三个必须先钉死的点：

**第一，「`-p` 发布宿主回环」在本平台是否有先例。** 全仓唯一的 `-p` 用法在统一镜像代理 `apps/core/src/sandbox_platform/proxy.py`：`-p 127.0.0.1:3128:3128`。但那个容器是**宿主 root 守护进程**起的——`Privilege.wrap()` 在进程本身是 root 时不加前缀，走的是宿主 `docker`，不是沙箱的免 root 守护进程。而沙箱的免 root 守护进程按 `userspace.py` 固定了 `DOCKERD_ROOTLESS_ROOTLESSKIT_DETACH_NETNS=true`（守护进程留在宿主网络命名空间、只有容器在 slirp4netns 命名空间里）。免 root 守护进程下 `-p` 能否在宿主回环真的产生监听，**本仓库从未验证过**；一期打样任务 `01-rootless-probe.md` 的「端口发布判定」写的恰恰是宿主 `ss -ltn` **不出现**由探针容器新增的监听端口。因此这条路径在本期是**未知**，必须作为硬前置打样项。

（**2026-11-03 修订（P1 结论并入）**：P1 打样**已实测通过**——rootlesskit 在宿主回环确实产生监听、`curl` 连通，结论留档见 [[tasks/phase3-desktop/RESULTS.md|三期留档]]。**该结论仍然成立**：`-p` 在本平台**可用**。决策 C 不用它，**不是因为它不可用**，而是因为产品形态上后端宿主机不该持有端口。）

**第二，转发容器归谁、谁回收。** 平台只回收自建资源。转发容器是平台自建的，必须进回收清单；而沙箱容器与依赖容器**零改动**（ADR 0003 的隔离契约不动），用户的沙箱镜像也**零改动**（镜像即产品的跨期约束）。

**第三，隧道这一跳的语义。** 隧道要跨机器（桌面端可能在另一台机器上），要支持同一沙箱的多个端口、同一端口的多条并发连接，还要有明确的断开 / 停止 / 服务重启语义。既有终端会话已经有一套成熟的口径（「服务重启即丢」），端口转发应当与之对齐而不是另发明一套。

## 决策

> **2026-11-03 第二次修订（决策 C）全文生效**：链路两点化、宿主零端口、Fallback B 升为唯一路径、用户机侧端口规则。以下各节按新口径写；立稿原文凡被取代处在句末标注「**（立稿口径，已按 2026-11-03 决策 C 废除/取代，留档）**」。

### 1. 端口转发的语义边界

- **只转发「用户显式指定的沙箱中的特定端口」**：不提供「转发沙箱全部端口」，不提供「自动发现端口」，不提供「按端口区间转发」。
- **链路只有两点：沙箱 ⇄ 用户机。** 转发只建立在「沙箱容器」与「用户所在机器（桌面应用 / CLI 客户端）」之间；**后端宿主是一个纯中继，不在链路上持有端口**——它既不向沙箱方向发布端口，也不向用户机方向监听端口。后端宿主上对沙箱端口的暴露面为**零**。
  - 立稿口径：「**监听面只在本机回环**：桌面端在**桌面所在机器**的 `127.0.0.1` 上开监听；后端侧在**后端宿主**的 `127.0.0.1` 上开端口。两端都只绑回环，**都不出本机**。」**（立稿口径，已按 2026-11-03 决策 C 废除/取代，留档）**
- **用户机侧监听只绑回环**：桌面端在**桌面所在机器**的 `127.0.0.1` 上开监听，**不出本机**、局域网不可达。
- **明确区分于 URL 代理**：URL 代理是「容器端口发布到宿主回环后，由宿主页反代对外提供一个可分享的网址」，已随原定三期整体退役（[[architecture/decisions/0001-项目定位与三期路线.md|ADR 0001]] 修订行）。端口转发是「桌面应用直连沙箱端口」，没有对外的网页入口、没有反代层、没有可分享地址。词汇表必须保持这一区分。

### 2. 转发容器：平台自建，接沙箱网络，由沙箱守护进程起，**不发布端口**

- 转发容器名 `<沙箱名>-fwd-<端口>`，带平台标签（用于枚举与回收）。
- 镜像：平台自有的转发镜像（`alpine/socat`，钉 digest），经统一镜像代理拉取到**沙箱的守护进程**（镜像拉取走代理是 ADR 0009 的既有口径）。**不改任何沙箱镜像**，用户镜像里不需要有 `socat`。
- **由沙箱自己的免 root 守护进程启动**：只有这样它才能接入沙箱网络并按容器名解析沙箱容器。沙箱容器与依赖容器本身零改动。
- **无端口发布**：转发容器**不发布任何端口**（立稿口径 `-p 127.0.0.1:<宿主端口>:<内部端口>` **已按 2026-11-03 决策 C 整体废除**——不是「技术上不行」，而是链路两点化后后端宿主不该持有端口）。容器主进程**保持常驻**即可（空转即可，如 `tail -f /dev/null`），**不在容器内做 TCP 监听**；`socat` 二进制由镜像提供，**专供 exec 字节泵使用**（第 3 节）。
  - **镜像特性提醒**：`alpine/socat` 的 ENTRYPOINT 是 `socat`，启动转发容器时**必须显式覆盖 entrypoint 与命令**（实测留档见 [[tasks/phase3-desktop/RESULTS.md|三期留档]] 第 6.1 节）。
  - 立稿口径：「命令：`socat TCP-LISTEN:<内部端口>,fork,reuseaddr TCP:<沙箱容器名>:<用户端口>`；`--restart=no`」+「**端口发布用 `-p 127.0.0.1:<宿主端口>:<内部端口>`**，复用 `proxy.py` 的 `-p 127.0.0.1:<port>:<port>` 写法与「只绑回环」的口径。」**（立稿口径，已按 2026-11-03 决策 C 废除/取代，留档）**
- `--restart=no` 仍成立：生命周期由平台显式管理。

### 3. 通道机制：`docker exec -i` 字节泵（**Fallback B 升为唯一路径**）

- **每条 TCP 连接 = 一个字节泵进程**：后端在**沙箱守护进程**下执行 `docker exec -i <转发容器> socat - TCP:<沙箱容器名>:<端口>`，该进程在转发容器内把字节桥到沙箱容器的目标端口；后端把 exec 的 stdin/stdout 与隧道 WS 做双向搬运。
  - 链路：`用户机本机监听 ⇄ 隧道 WebSocket（Bearer）⇄ 后端 exec 字节泵 ⇄ 转发容器 ⇄ 沙箱容器端口`。
- **这是原 Fallback B**，立稿时它是「`-p` 不成立时的备案路径」，**现已升为唯一路径**。
  - 立稿口径：「**Fallback B（`-p` 不成立时的备案路径）**：转发容器仍起、仍接沙箱网络，但**不发布端口**；宿主侧改用 `docker exec -i <转发容器> socat - TCP:<沙箱容器>:<端口>` 建立双向字节管道，平台侧把字节泵到宿主回环端口。」**（立稿口径，已按 2026-11-03 决策 C 取代：不再把字节泵到宿主回环端口，而是直接与隧道 WS 对接；`exec` 的调用方是后端服务，命令在沙箱守护进程下执行）**
- **代价：从「备案待评估」转为「既定既接受」**：每条连接一个 exec 进程；延迟与吞吐不如直连；`exec` 管道非 TTY，需要额外分帧与超时处理。
  - 立稿口径里的这两条代价描述**仍然成立**，只是它们不再是「若 P1 不通过才需承担的降级」，而是**本期的既定形态**。
- **优点**：完全不依赖 `-p`，只依赖终端伪终端桥接已经在用的 `docker exec` 机制；后端宿主上不产生任何转发端口。
- **P1 结论的处置**：P1 已实测 `-p` 在本平台**可用**（[[tasks/phase3-desktop/RESULTS.md|三期留档]]）。**该结论不撤销**，但**不再采用**——决策 C 是产品形态判断，不是技术可行性判断。`-p` 路径与宿主端口区间分配**整体废除**（含「宿主端口占位 / 冲突探测 / 换端口重试 / 回退」一整套概念）。

### 4. 用户机侧端口规则

端口的**选择权与冲突处理全部落在用户机**（桌面端），后端不感知本机端口：

- **默认 = 容器端口**：新建转发时本机端口默认填入容器端口。
- **可编辑、不可为空**：用户可改本机端口；**不能留空**（空值无意义，直接视为非法输入，表单层拦截）。
- **被占自动换空闲端口**：目标端口已被占用时，桌面端**自动改用一个空闲端口**，并**显示实际生效的端口**——界面显示的必须是**实际值**，不得显示用户输入值。
- **允许 <1024（低端口）**：本期**允许**用户填写 <1024 的端口。OS 差异已知并接受：Windows 可绑定；macOS 现代版可绑定；**Linux 上非 root 不可绑定**。目标平台以 **Windows 为主**，故本期不做权限提升、不做端口范围限制；若桌面端跑在 Linux 且用户填了低端口，**必须明确报错**而不是静默失败。
- **宿主侧的对应概念一并废除**：端口区间（默认 `18000-18999`）、端口占位、「绑定失败换端口重试」等**全部随 `-p` 一并废除**——宿主上不再有平台分配的转发端口。
  - 立稿口径：「### 4. 宿主端口自动分配与占位」整节（后端宿主回环端口由平台自动分配、可配区间默认 `18000-18999`、分配前做端口可绑定探测、分配结果落进转发记录形成占位、绑定失败换端口重试、端口与转发记录一一对应停止即释放）。**（立稿口径，已按 2026-11-03 决策 C 整体废除，留档）**

### 5. 隧道协议

- 路径：`/api/forward/tunnel/{forward_id}`；**一条 WebSocket 对一条 TCP 连接**（本期不做多路复用）。
- 客户端 → 服务端：二进制帧 = 透传字节；文本帧 = 控制（本期仅留扩展位）。
- 服务端 → 客户端：二进制帧 = 透传字节；文本帧 = `{"type":"hello", ...}` / `{"type":"error","message":"..."}`。
- 关闭：任一侧 EOF 即关另一侧；转发不存在或已停止 → 关闭码 `1008`；正常关闭 `1000`。
- 鉴权：桌面 Rust 客户端可以直接设 `Authorization: Bearer`，**不需要票据**（票据只服务于浏览器侧的 WebSocket）。
- 帧协议风格与终端桥接保持一致（二进制 = 字节、文本 = 控制），便于前端 / Rust 两侧共用同一套心智。
- **服务端侧的桥接目标**：不是「连 `127.0.0.1:<宿主端口>`」，而是**起一个 `docker exec -i` 字节泵**（第 3 节）并与 WS 对接；**连接断开 → 该 exec 进程立即回收**（不留僵尸 exec 进程）。

### 6. 转发管理 REST

- `GET /api/forwards` → 裸数组（与既有接口风格一致）。
- `POST /api/forwards` → 入参 `{sandbox, port}`；沙箱不存在 / 已停止 / 端口非法 → 明确错误。
- `DELETE /api/forwards/{id}` → 停止转发：停并删转发容器、删记录。
  - 立稿口径里的「**释放宿主端口**」**已按 2026-11-03 决策 C 废除**（宿主侧不再有端口）。
- **转发记录不含本机 / 宿主端口字段**：字段为 id / sandbox / container_port / state / created_at / updated_at。

### 7. 生命周期与清理语义

| 场景 | 口径 |
|---|---|
| 建立转发 | 记录 + 起转发容器（幂等：同名同端口的转发容器已存在则复用） |
| 沙箱停止 | 该沙箱的转发容器一并停止；**记录保留** |
| 沙箱启动 | 不自动重建；隧道建立时若容器缺失则幂等重建 |
| 停止转发 | 停并删转发容器 + 删记录 |
| 沙箱删除 | 转发容器与转发记录**纳入回收清单并被回收**（平台自建资源） |
| 后端服务重启 | **全部转发会话丢失**，启动时清理上次遗留的转发容器与记录（对齐终端会话「服务重启即丢」） |
| 桌面端断开 | 桌面应用退出 → 本机监听随进程退出而消失（监听是进程内内存态，无残留）；**单条隧道 WS 断开 → 只关那一条本机连接**（连接级上报），**本机监听保留**、活到用户显式 `stop_forward` / 「停止转发」才关（不留僵尸监听）；对应的 exec 字节泵进程**立即回收**。**（立稿口径「隧道 WS 断开即关本机监听、界面显示『转发已断开』」已按 2026-11-03 实现轮修订**——监听是用户开启的一项能力，不是单次连接的产物；落点见 [[tasks/phase3-desktop/06-port-forward-desktop.md|任务 06]]） |
| 隧道连接断开 | 对应的 `docker exec` 字节泵进程**立即回收**，不留僵尸进程 |

（立稿口径的「分配宿主端口」「释放宿主端口」两处**已按 2026-11-03 决策 C 废除/取代，留档**。）

### 8. 能力落点

- 转发编排（容器起停、标签枚举、清理）落**核心包** `apps/core/src/sandbox_platform/forwarding.py`，是可复用服务模块；服务端（`sandbox_console`）只做编排与转译。
- **命令行本期不接转发**：`sandboxctl` 保持直连核心包、不改造成服务客户端（ADR 0009 推迟 CLI 服务化的口径不变）。**CLI 要接转发，前提是先把 CLI 服务化**——本期不做；**架构上不排除**后续支持。

## 影响

- **P1 的不确定性已被决策 C 取代**。立稿时最大的未知是「免 root `-p` 能否在宿主回环真的产生监听」；该问题**已实测通过**（结论仍成立），但**路径不再采用**。真正的不确定性转移为「**exec 字节泵的吞吐与并发连接数**」——每条连接一个 exec 进程是本期既定形态，不是待评估项。
- **后端宿主上的暴露面收窄到零**。立稿口径的「宿主回环这一跳不受令牌保护」（后端宿主上的任意本地进程都能直连被发布的端口）**随之消失**——宿主上不再有平台发布的转发端口，后端服务只监听它自己的 API 端口。立稿中提出的收紧方向（「宿主回环端口只在隧道建立期间短暂开启」/「加平台内部口令」）**一并作废**，本期无需处理。
- **用户机侧端口的可用性成为新的失败面**。端口被占用是常态（不是异常），因此桌面端必须**自动换空闲端口并显示实际值**；界面若显示用户输入值而实际换了端口，用户会连不上。
- **低端口（<1024）的 OS 差异是已知边界**。Windows 可绑、macOS 现代版可绑、Linux 非 root 不可绑；目标平台 Windows 为主。若用户在 Linux 上跑桌面端并填了低端口，**必须明确报错**。
- **端口转发不是 URL 代理，但极易被误读**。两者曾形态相似（「容器端口发布到宿主回环」这一步），现在宿主不再发布端口，形态差异更大、更易区分。词汇表仍须显式区分，界面文案也要写明「访问端口需要桌面应用」。
- **多路复用被推迟**：一条 WS 对一条连接，简单可靠，但每条 TCP 连接多一次 WS 握手 + 一次 exec。高并发场景（如浏览器同时开几十个并发请求到同一个沙箱端口）会有握手与进程开销。这是可接受的取舍，因为本期目标是开发调试场景。
- **服务重启丢转发会话**会让用户重连时需要重建。沿用终端会话的既有口径而不是发明新语义，是为了少一套状态机、少一类用户困惑。
- **转发容器是新的平台自建资源**，意味着删除沙箱的回收清单多了一项、`reclaim_plan` 的输出变了，既有验收里断言回收清单结构的用例要跟着更新。
- **用户镜像零改动**这条守住了（转发容器是独立的平台镜像），但代价是多了一个需要平台自己维护的镜像（拉取、digest 固定、代理缓存命中）。
- **转发容器的主进程语义变了**：从「容器内 TCP 监听」改为「容器常驻、不监听」，`socat` 二进制专供 exec 字节泵使用。
