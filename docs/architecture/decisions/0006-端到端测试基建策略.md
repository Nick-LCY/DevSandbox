# 0006. 端到端测试基建策略

- 日期：2026-10-29
- 状态：已接受

## 背景

项目的核心价值是 agent 自主完成端到端测试。要支撑这个闭环，测试基建必须同时满足两点：agent 能低成本地反复验证（否则每轮修复都很贵），以及每轮验证的结论可信（否则 agent 会被错误结论带偏）。

还要解决一个常见陷阱：环境没起来和代码有 bug 长得一样，agent 分不清就会去改不该改的代码。

## 决策

- 脚本化 Playwright 为主：测试脚本进仓库，可回归、可重复执行。
- 探索式现场操作为辅：测试失败或需要视觉走查时，由 agent 现场驱动浏览器、截图并分析。
- 每个测试用例独立数据库：用模板库秒级克隆 + 种子脚本，避免用例之间数据互相污染。
- 运行前健康检查门禁：依次等待依赖就绪 → 执行数据库迁移 → 灌入种子数据，全部通过才允许开始跑测试。
- 页面元素统一 `data-testid` 规范，测试脚本只按测试标识定位元素，不依赖样式与文案。
- 截图与 trace 留在用户声明挂载的代码目录，不上传 MinIO。集中产物出口已取消；用户在 agent 报告完成后再做人工验收。
- agent 用截图做自己的多模态修正闭环：截图既是给人看的证据，也是 agent 判断修复效果的输入。

## 影响

- 脚本化优先意味着前期要投入编写测试基建，换来可重复回归与更低的单次验证成本。
- 独立数据库与模板克隆增加秒级准备时间，换来用例间完全隔离；模板库需要随数据模型变更同步维护。
- 健康检查门禁把「环境没就绪」与「代码有 bug」区分开，能显著降低 agent 的无效修改；但门禁失败时 agent 必须能自行判断原因并重试或修环境，门禁的错误提示要足够清楚。
- 产物不上传对象存储，链路更短、没有脱敏负担；代价是产物没有集中归档与远端分享能力，交付前需要用户自行取走。
- `data-testid` 是约定而非强制，示例项目与用户项目都要遵守，否则脚本化测试会频繁因选择器失效而中断。
