# 文件注入轮：创建沙箱时把宿主文件复制进沙箱

> 日期：2026-11-02
> 一期需求见 [[prds/sandbox-platform.md]]，二期需求见 [[prds/phase2-console.md]]，控制台模板轮见 [[prds/console-templates.md]]

## 背景

平台把宿主文件带进沙箱的唯一通道是「用户声明挂载」，而挂载要过一道预检：平台在创建沙箱时，对每条挂载声明以沙箱用户身份检查「可读且可穿过」（实现是外部 `test -r` / `-x`，按 mode 位的 owner / group / other 比对，不识别 POSIX ACL）。预检不过，声明直接被拒。

这道预检让一批常用宿主文件进不了沙箱：0600 的 ssh 私钥、pi 凭证 `auth.json`，以及 0700 的目录。这些文件要么属主是用户本人、要么属于别的账号，mode 位上沙箱用户既不是 owner 也不在匹配组里，预检必然失败。

绕不过去的原因是时序，不是权限模型本身：

- **沙箱用户在创建那一刻才建立**，uid 动态分配、创建失败即回滚删除。所以「提前给某用户 / 组授权」在时序上没有授权对象——ACL 条目与专用组都要指向一个具体的 uid，而那一刻它还不存在。
- **敏感原件不能靠放开权限位解决**。0600 / 0700 的原件一旦放开 other 位，本机所有本地账号都能读私钥与凭证，暴露面失控。

四条替代路线都评估过，逐条否决：

1. **给宿主文件加 ACL 授权** — 预检按 mode 位比对、看不见 ACL，等于要把预检整体改造成 ACL 感知，还得要求宿主装 acl 包并改造创建流程。改造成本与新增依赖都落在预检这条主路径上。
2. **放开原件的 other 位** — 本机所有本地账号可读私钥与凭证，暴露面失控；等于为一次性的沙箱需求永久放宽宿主凭证。
3. **人工维护中转副本** — 副本脱管：内容要人工同步、副本何时清理靠人记、清理不及时就是一份新的长期暴露面。
4. **改用 HTTPS + 访问令牌替代 ssh 密钥** — 改变了既有的 ssh 使用习惯，且令牌文件本身的权限问题同源：照样需要一份沙箱用户读得到的宿主文件，预检照样拦。

选定机制是**在创建流程内做「复制 + chown」**：时序上发生在专属用户创建之后、容器启动之前，把用户声明的宿主文件复制到沙箱用户家目录内的暂存目录（具体命名实施时定），属主改为沙箱用户，再以只读方式挂载进容器。

这条链路上每个环节都指向已有契约：

- 副本属主即沙箱用户，预检天然通过——不需要预检改造，也不需要宿主授权动作。
- 副本落沙箱用户家目录，随沙箱删除时被既有的「回收用户家目录」承诺自动销毁，不新增回收责任。
- 原件零接触：不 chmod、不 chown、不修改、不删除。
- 复制与属主设置经平台既有特权执行机制完成，与建用户同路。

## 目标

- **声明即得**：用户在创建沙箱时声明一组注入文件（宿主路径:容器路径），容器内即可读到内容与原件一致的副本。
- **原件守恒**：注入过程对原件不做 chmod、不 chown、不修改、不删除。
- **副本生命周期等于沙箱生命周期**：停止 / 启动期间保留，删除沙箱自动消失。
- **敏感凭证不进容器前无需任何权限放开**：ssh 私钥与 pi 凭证 `auth.json` 是两个代表场景。

## 非目标

- **命令行零改动**：本轮命令行不加注入参数；「sandboxctl 增加文件注入参数（如 `--file`）」登记为 TODO，等文件注入轮核心能力落地后补。
- **会话持久化不在本轮**：用户另有方案，另行解决。
- **不做「重新注入 / 刷新副本」操作**：复制是创建时快照，沙箱运行期间宿主原件变更不回灌；要新鲜凭证就重建沙箱——此代价必须在用户文档明示。
- **不支持副本可写、不支持容器写回宿主**：容器内一律只读。

## 方案

四个工作包按依赖顺序推进，01 → 02 → 03 → 04。

### 工作包一：核心包注入能力（apps/core）

- **做什么**：创建请求新增注入文件声明字段（字段名建议 `files`，格式「宿主路径:容器路径」，固定两段，没有读写标记——容器内强制只读）；生命周期在用户创建后执行「复制 → chown 沙箱用户 → 文件 0600 / 目录 0700 → 只读挂载」；校验沿用挂载声明那套——宿主路径必须已存在、必须是绝对路径、不得含逗号、不得命中宿主敏感目录拒绝清单（`/etc`、`/proc`、`/sys`、`/dev`、`/boot`、`/root`、宿主 Docker 套接字、平台数据根）。
- **复制语义（首版）**：支持普通文件与目录，目录递归复制；符号链接一律报错（既不跟随、也不复制链接本身），避免复制出非预期内容；多条声明之间宿主路径不得重复、容器路径不得重复冲突；容器路径不得与固定套接字挂载点冲突（沿用挂载那套检查）。
- **不做什么**：不改造挂载预检本身，不新增预检语义；不做副本刷新、不做可写副本、不做容器写回宿主；不引入宿主机 acl 包等新依赖。
- **验收方向**：注入预检、复制语义、符号链接报错、敏感路径拒绝、路径冲突、回收行为六类各有覆盖。

### 工作包二：控制台服务端与模板字段（apps/web/backend）

- **做什么**：创建请求透传 `files` 字段；`TemplateConfig` 新增 `files`；落盘与回填沿用既有口径——用 `exclude_unset` 保住「字段是否出现」，应用语义是**出现字段整组替换、缺失字段保持表单现状**。
- **不做什么**：不改模板的合并语义与占位符口径（模板声明仍原样透传）；不改既有接口的路径与响应结构。
- **验收方向**：含 `files` 的模板「保存 → 回填 → 真机全流程」跑通。

### 工作包三：前端交互（apps/web/frontend）

- **做什么**：新建沙箱抽屉新增「文件注入」声明区（与挂载区同级）；模板保存 / 加载覆盖 `files`；既有交互规范（toast、校验提示、可搜索控件）不变。
- **不做什么**：不引入新交互范式、不改挂载区既有形态。
- **验收方向**：vitest / typecheck / build 全绿并新增覆盖；真机用例补文件注入流程。

### 工作包四：真机验收与文档收口

- **做什么**：质量基线全绿（后端 pytest、前端 vitest / typecheck / build、Playwright 真机既有 24 条不回归并补文件注入用例）；`apps/web/backend/API.md` 增补 `files` 字段与错误口径；词汇表加「文件注入」词条；实施轮以 ADR 固化「复制 + chown 优于 ACL 预检改造」的机制选型及四条否决理由。
- **不做什么**：不改既有架构决策的结论，不重写历史任务的完成标准。
- **验收方向**：命令行行为零变化（本轮命令行零改动）。

## 验收标准

- [x] 对 0600 的 ssh 私钥与 pi 凭证 `auth.json` 原件，不做任何 chmod，声明注入后创建沙箱成功，容器内能读到副本内容。
- [x] 创建前后原件的权限位、属主、内容、mtime 完全不变。
- [x] 容器内对副本路径写入失败（只读生效）。
- [x] 删除沙箱后副本随家目录消失、原件仍在。
- [x] 含 `files` 的模板：保存 → 回填（出现整组替换、缺失保持现状）→ 真机全流程通过。
- [x] 质量基线：后端 pytest 既有基线全绿并新增覆盖（注入预检、复制语义、symlink 报错、敏感路径拒绝、路径冲突、回收）；前端 vitest / typecheck / build 全绿并新增覆盖；Playwright 真机既有 24 条不回归并补文件注入用例；命令行行为零变化。
- [x] 文档同步：`apps/web/backend/API.md` 增补 `files` 字段与错误口径；词汇表加「文件注入」词条；实施轮以 ADR 固化「复制 + chown 优于 ACL 预检改造」的机制选型及否决理由。
